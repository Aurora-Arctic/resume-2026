# CI Setup — Summary

Full implementation history: [claude-docs/transcripts/CI-SETUP.md](transcripts/CI-SETUP.md)

- Two phase workflows: `pr-gate.yml` (PR → `main`, `staging`, or `release/**`) and `merge-queue.yml` (`merge_group`), both composed from small reusable per-check workflows (`lint`, `format`, `typecheck`, `vitest`, `build`, `playwright`, `audit`, `gitflow`).
- `staging` gets the same CI/branch-protection treatment as `main`, but via its own repo ruleset ("Staging", mirroring "Main") rather than a `branches:`-list edit — the "Main" ruleset targets the dynamic `~DEFAULT_BRANCH`, and `main` stays the repo's default branch, so it can't also cover `staging` by itself. `staging` is the normal day-to-day PR base (opt-in, not default). Dependabot (`.github/dependabot.yml`) targets `staging` on all three ecosystems, same as human PRs.
- **Gitflow branch-source rules** (`gitflow.yml`, modeled on the [gitflow-branching-rules article](https://medium.com/@ariifischbein/automate-gitflow-branching-rules-with-github-actions-d672f80d335b), with `staging` standing in for the article's `develop`): a blocking, always-run check (no path-filter, like `format`) validating a PR's source branch against its target — `main` only accepts `release/MAJOR.MINOR.PATCH`/`hotfix/*`, `staging` accepts `feature/*`/`release/MAJOR.MINOR.PATCH`/`hotfix/*`, and `release/*` accepts `staging`/`hotfix/*`. Release branches must match the precise `release/MAJOR.MINOR.PATCH` semver naming (e.g. `release/1.2.3`) to count as a valid source — `.claude/skills/create-release` always produces a name in that form. Branch protection/rulesets can gate a target branch but can't express "only branch X may merge into target Y" — this check fills that gap. `main` is now promoted via `release/*` (or `hotfix/*`) PRs rather than direct `staging` → `main` PRs. Not called from `merge-queue.yml` — see the comment in `pr-gate.yml`'s `gitflow` job for why. `release/**` branches have no ruleset of their own yet (manual follow-up, like the "Staging" ruleset below).
- **Gitflow-aware skills**: `.claude/skills/create-pr` proposes only Gitflow-valid PR targets for the current branch (rather than defaulting to `main`) — except `hotfix/*` branches, which skip the target question and always get two PRs, into both `main` and `staging`, since a hotfix has to land in production and the mainline alike; `.claude/skills/create-feature`/`create-hotfix` branch off `staging`/`main` respectively; `.claude/skills/create-release` computes the next semver version from the latest `vMAJOR.MINOR.PATCH` git tag (major/minor/patch, asked via a question, patch by default), creates `release/<version>` + a `v<version>` tag, pushes both, and opens a PR into `main` summarizing every PR actually merged into `staging` as part of the release, with author attribution.
- Every check runs inside the Docker `testing` stage via each job's `container:` key; `GITHUB_WORKSPACE` is copied to `/app` via the local composite action `.github/actions/checkout-to-app/`.
- `pr-gate` jobs each have their own `concurrency` group (cancel-in-progress) except `build-image`, which is deliberately `cancel-in-progress: false` — cancelling it mid-push can corrupt the shared, content-addressed GHCR layer cache.
- Path filtering (`dorny/paths-filter`, PR-gate only) skips irrelevant checks on a docs-only or scoped diff. Each job is gated via a `should-run` workflow_call input evaluated inside the job (not a job-level `if:` on the caller) — a job-level `if:` would report the check under a different name and permanently stall required-status checks.
- PR comments and job summaries are built from shared local composite actions: `.github/actions/pr-comment/`, `job-summary/`, `timer-start/`, `timer-elapsed/`.
- Local testing via [`act`](https://github.com/nektos/act): `make act-lint|format|typecheck|vitest|build|playwright|test`. `audit.yml` and `build-image.yml` are excluded.
- Both `npm run test:e2e` and `test:e2e:coverage` build-and-serve on port 8001 by default (`playwright.config.ts`, overridable via `PORT`) — deliberately not Gatsby's usual `:8000` (`npm run develop`/`serve`), so e2e never collides with, or silently reuses, a dev server already running there, in CI or locally alike.
- Enabling the merge queue requires a manual, one-time "Require merge queue" setting in GitHub branch protection — `merge-queue.yml` never triggers without it.
- `.github/dependabot.yml` — weekly PRs for npm deps, GitHub Actions versions, and the Docker base image pin.
