# Skills — Implementation Record

This document is a transcript of the work done around `src/components/Skills` — the categorized technical-skills section. See [RESUME.md](RESUME.md) for the shared section-order, data-model, and layout-flexibility decisions behind this whole batch of scaffolding work; this document covers only what's specific to `Skills`.

## Why it exists

Both the user-supplied bridgeviewit.com guide and general search results agree technical skills should be grouped by category (Languages, Frameworks, Cloud, DevOps, etc.) rather than one flat list — easier to scan for a human reviewer and gives ATS keyword matching cleaner groupings. Given the user's own background (backend, serverless infra, developer experience/CI-CD-tooling), the placeholder category _labels_ in `resumeData.skills` were chosen to already reflect that shape (`Languages`, `Cloud & Infrastructure`, `CI/CD & Tooling`, `Frameworks & Libraries`) — this is structural scaffolding, not the "fill out content" work that's explicitly deferred, so the labels are a reasonable placeholder but the individual skill values inside each category remain generic.

## Current state

- `index.tsx`: takes `skills: SkillCategory[]`, renders a `<section aria-labelledby="skills-heading">` with an `<h2>` and a `<dl>` — one `<dt>`/`<dd>` pair per category, skills joined with `, `.
- `index.scss`: vertical margin, bold `<dt>`, no grid — deliberately stacked, consistent with the rest of the page staying single-column for now (see [RESUME.md](RESUME.md)).
- `index.test.tsx`: renders two sample categories, asserts each category label and its joined skill list appear.

## Per-skill list markup, 3-column grid, and diamond bullets (2026-08-09)

Requirements from the user: move `Skills` later in the section order (see [RESUME.md](RESUME.md) for that change), lay its groups out in a 3-column grid on the web, render each `dd` as a real list of items instead of a joined string, style that list with a `$wine`-colored diamond bullet in place of the default disc, and make `dt` read as a slightly larger/bolder label than `dd`.

- **Markup**: `dd`'s comma-joined string became a nested `<ul>`/`<li>` per skill. The grid-container class (`resume-skills__groups`) was added directly to the existing `<dl>` rather than introducing a new wrapper `<div>` around the `.resume-skills__group` children — a `<dl>` is only valid when its children are `dt`/`dd` pairs or `<div>`s that _directly_ wrap `dt`/`dd` pairs, and the existing `div.resume-skills__group` children already satisfy that; wrapping another `<div>` around those group divs would have broken the content model. `dl > div > dt + dd(> ul > li)` is valid HTML and is also a net accessibility improvement over the old flat comma-joined string — screen readers now get real list semantics (item count, per-item navigation) instead of one run-on string.
- **3-column grid**: `resume-skills__groups` gets `display: grid; grid-template-columns: repeat(3, 1fr)` gated behind `$breakpoint-desktop` — reusing the site's one existing breakpoint (see [RESUME.md](RESUME.md)) rather than introducing a new one, since `.resume-skills` already spans the full paper-card width at that breakpoint (`grid-column: 1 / -1` in `Resume/index.scss`), giving three columns comfortable room. Below the breakpoint, and always in print, it stays single-column/stacked — required its own explicit `@media print { display: block }` inside `resume-skills__groups` rather than relying solely on `Resume/index.scss`'s top-level `@media print` reset, since a `min-width` query can still match when printing from a wide viewport.
- **Diamond bullets, first attempt via `::marker`, landed via `::before`**: initially implemented as `li::marker { content: '◆ '; color: $wine-stained; }` — `::marker` is the CSS-native list-bullet mechanism and none of the codebase's existing `::before` usages (button fill animation, theme-toggle icon, tooltip arrow) are actually list bullets, so there was no real precedent pulling toward `::before`, and `::marker` content is excluded from the accessibility tree by default (unlike literal text), which is the desired behavior for a decorative bullet. However, the user asked to nudge the diamond's vertical position up by `0.125rem`, and `::marker`'s browser-implemented allowed-property list (color, content, font properties, white-space, animation/transition, unicode-bidi, direction) excludes positioning properties (`top`, `transform`, `vertical-align`) — there's no way to offset it. Switched to `ul { list-style: none; }` + `li { position: relative; }` with `li::before { content: '◆'; position: absolute; left: -1.25rem; top: -0.125rem; }`, matching the codebase's existing convention of using `::before` for positioned decorative shapes (Tooltip's arrow uses the same absolute-positioning approach). The diamond glyph still stays in CSS only, never in JSX text, to avoid it being read aloud per item by a screen reader.
- **Bullet color is theme-split**: `_typography.scss` already documents that raw `$wine` is low-contrast against the dark (default) card background, which is why link color splits into `$wine-stained` (dark mode) / `$wine` (light mode). The diamond bullet follows that exact same pattern (`$wine-stained` by default, `html[data-theme='light'] .resume-skills dd li::before { color: $wine; }`), rather than using plain `$wine` everywhere, to avoid the same known contrast problem recurring on a second element.
- **`dt`/`dd` type scale**: `dt` became `font-weight: 500; font-size: 1.125rem` — reusing the site's only existing "bold" weight (used uniformly on `h1`–`h4`) and the `h4` font-size rung, rather than inventing new values. `dd` was left with no explicit override, so it stays at the inherited body default (`1rem`/`300`) — now reading correctly lighter/smaller purely by contrast with `dt`. Deliberately did not switch `dt` to `$font-heading` (Syne, used for real headings/entry titles) since that would visually compete with actual section/entry headings when repeated several times down the Skills list.
- **Incidental fix**: `dt { margin-bottom: 0.25rem 0; }` was invalid CSS (`margin-bottom` only accepts one value) and silently did nothing — replaced with the `margin: 0 0 0.25rem;` shorthand already used elsewhere in this file while touching the same rule.
- `index.test.tsx` updated to assert individual skill items and list roles (`getAllByRole('list')`/`getAllByRole('listitem')`) instead of the old joined-string assertions.

## Expandable sub-items, arrow bullets, and section-wide tooltip dismissal (2026-08-09)

Requirements from the user: several skills bundle related sub-technologies in a parenthetical (`'JavaScript (ES, jQuery, TypeScript)'`, `'React (Next.js, Gatsby)'`, `'Vue (Nuxt.js)'`, `'AWS (CloudFormation, Serverless, Load Balancing)'`, `'Linux (Apache2, Nginx, PM2, Gunicorn)'`); these should become click-to-expand items revealing the sub-technologies as their own list below, with the diamond bullet swapping for an arrow that rotates to point down when expanded, a hover state recoloring the item text and enlarging the arrow ~5%, and a "Click for more info" tooltip hint. Dismissing any one of these tooltips should clear every tooltip in the Skills section at once (not the single one, not the whole site).

- **Data model, not text parsing**: first drafted as a regex parsing `'Label (a, b, c)'` back out of the existing plain strings at render time, keeping `SkillCategory.skills: string[]` untouched. The user explicitly asked for a real data-model change instead — first as a minimal `string | { label; subItems }` union (touching only the 5 entries that needed it), then further refined to a single uniform shape for **every** skill so the whole array stays consistent rather than mixing two representations: `SkillEntry = { label: string; subItems?: string[] }`, `SkillCategory.skills: SkillEntry[]`. All 32 entries in `resumeData.skills` became `{ label }` objects, `subItems` present only on the 5 that need it. This touched `Resume/index.test.tsx`'s fixture too (its `skills` field, unrelated to what it actually asserts — just the `<h2>` heading) — confirmed via exploration to be the only other file with a `SkillCategory` fixture; no e2e spec references skill content at all.
- **Expand/collapse markup**: a skill with `subItems` renders as `<li className="resume-skills__skill resume-skills__skill--expandable">` wrapping a `<button aria-expanded aria-controls>` (native `<button>`, matching the codebase's only interactive-element convention — no `role="button"`/manual `onKeyDown` precedent exists anywhere in `src/`, and `jsx-a11y` is enabled) inside a `Tooltip`, followed by the sub-item `<ul>`. The sub-list is **always mounted** in the DOM and toggled via the `hidden` attribute rather than `{expanded && ...}` conditional JSX — this lets a `@media print { [hidden] { display: block; } }` rule force it visible regardless of on-screen collapse state (the printed resume should always show full detail, consistent with the site's standing print-is-complete convention), and makes RTL assertions straightforward (`toBeVisible()`/`not.toBeVisible()`).
- **Arrow bullet via `:has()` + CSS custom properties**: the arrow replaces the diamond only for `--expandable` items (`content: '▶'`), rotating via `transform: rotate(var(--skill-arrow-rotate, 0deg))` — a `--skill-arrow-rotate: 90deg` custom property set by a `--expanded` modifier class (matching the site's existing `--modifier` BEM convention, e.g. `theme-toggle__facet--out`). Hovering/focusing the nested `<button>` needs to scale the ancestor `<li>`'s own `::before` pseudo-element — no plain CSS combinator reaches an ancestor's pseudo from a descendant's hover state, so this used `:has()` (already an established pattern in this codebase, `Tooltip/index.scss`'s `:has(:focus-visible)`), setting a second custom property (`--skill-arrow-scale: 1.05`) that composes independently with the rotate property in one `transform` declaration — so hovering an already-expanded arrow still scales without fighting the rotation.
- **A real specificity bug caught before landing**: the existing diamond-bullet rule is `.resume-skills dd li::before` (1 class + 3 element/pseudo-element selectors). A first draft of the arrow override used a single-class selector (`.resume-skills__skill--expandable::before`, 1 class + 1 pseudo-element) — CSS specificity compares class-count before element-count, so 1-class-vs-1-class ties there and the base rule's extra element selectors (`dd`, `li`) would have won on the next tuple position, silently keeping `content: '◆'` and never showing the arrow at all on screen (only in print, where the value happens to coincide). Fixed by writing the override as a compound-class selector, `.resume-skills__skill.resume-skills__skill--expandable::before` (2 classes), which now correctly outranks the base rule regardless of its element count.
- **Hover color**: the toggle button's text and the arrow both recolor to the same diamond color (`$wine-stained` dark / `$wine` light, same theme-split as the diamond and site links) on `:hover`/`:focus-visible`, using `$theme-transition-duration`/`$theme-transition-easing` (400ms/ease-in-out) — the dominant transition convention across `_buttons.scss`, `ThemeToggle`, `Layout`, and `Tooltip` itself; `_typography.scss`'s link-hover (a literal 200ms) is the one outlier in this codebase and wasn't the pattern to match here.
- **Print reverts the arrow to a diamond**: the arrow glyph and its rotation are a screen-only affordance for an interaction that doesn't exist on paper, so `@media print` inside the `--expandable` rule resets `content: '◆'; transform: none;` — same bullet as every other skill in the printed resume.
- **Section-wide tooltip dismissal required extending `Tooltip` itself** — see [TOOLTIP.md](TOOLTIP.md) for the `onDismiss`/`dismissTooltips`/`TOOLTIP_DISMISS_EVENT` mechanism. `Skills` computes the flat list of every expandable item's tooltip id once per render (cheap, ~32 items total, no `useMemo`) and passes it down so any one dismiss can clear the rest — chosen over a `group` prop on `Tooltip` since the caller already knows exactly which ids it owns.
- Tooltip/sub-list ids are generated as `${slugify(category)}-${slugify(label)}-tooltip`/`-sublist`, not the earlier regex-derived approach, since `category`/`label` are now real fields rather than substrings pulled out of parenthetical text.

## Arrow moved onto the button, button-background exemption, sub-item diamond tuning (2026-08-09)

Follow-up feedback on the above: the toggle button shouldn't get the shared keycap-fill background every other `<button>` in the app gets; the arrow should be smaller by default and grow (not just recolor) on hover; the arrow itself needs to be part of the button's own clickable hit-area, not a separate unclickable `::before` on the `<li>`; and the sub-item diamonds shouldn't be shrunk, just recolored (`$wine-drenched` default, `$wine-stained` on hover).

- **Arrow moved from `<li>::before` to `<button>::before`**: dropped the `:has()`-based approach entirely — with the arrow living on the button itself, its own `:hover`/`:focus-visible` states apply directly, no ancestor-reaching pseudo-class needed. The button uses a negative-margin/matching-padding trick (`margin-left: -1.25rem; padding-left: 1.25rem;`) to pull its own box into the bullet gutter so the arrow (`::before`, positioned within that padded region) sits exactly where the diamond bullet would, while remaining part of the button's own hit area.
- **Exempted from the shared button-background fill**: `_buttons.scss`'s keycap-style hover/focus/active fill (`::before` background swap) is meant for icon/action buttons, not a plain-text expand toggle. Extended the existing `:not(:where(.tooltip__dismiss))` exemption to `:not(:where(.tooltip__dismiss, .resume-skills__skill-toggle))` — `:where()` keeps the exclusion at zero added specificity, consistent with how `.tooltip__dismiss` was already exempted.
- **Arrow size/scale retuned**: smaller at rest, growing on hover/focus rather than just recoloring — final values `font-size: 0.625em` at rest, `--skill-arrow-scale: 1.2` on hover/focus (composed with `--skill-arrow-rotate` in one `transform`, same mechanism as before).
- **Sub-item diamonds**: kept at the same `font-size: 1rem` as the top-level diamonds (not shrunk, reverting an earlier size reduction). Color now comes from the shared base rule (see "Diamond bullets extracted into `_lists.scss`" below) rather than a Skills-local override.

## Tooltip placement: left-of-item on desktop, above-and-left-aligned on mobile (2026-08-09)

Follow-up request: the "Click for more info" tooltip on an expandable skill (positioned per-instance, per `Tooltip`'s own convention — see [TOOLTIP.md](TOOLTIP.md)) needed explicit placement rather than falling back to the tooltip's default box position, plus a mobile-specific arrangement since there often isn't room beside a skill item on a narrow viewport.

- **Desktop** (`$breakpoint-desktop` and up): tooltip sits to the left of the item, vertically centered on the label text, with its arrow on its own right edge pointing back at the trigger — the mirror image of `ThemeToggle`'s `.theme-toggle-tooltip` (which sits above its trigger with a downward arrow). Getting this right required overriding the base `.tooltip`'s `::after` hover-bridge (Tooltip/index.scss), which by default extends _downward_ from a tooltip placed above its trigger (`top: 100%`) — this instance needed it to extend _rightward_ instead (`left: 100%`, full height, width driven by `--tooltip-bridge-reach`), so both the visible gap and the bridge width were kept in sync.
- **Mobile** (below `$breakpoint-desktop`): tooltip sits above the item instead, left-aligned with the _li's own_ left edge (not the bullet/arrow gutter, which sits further left via negative margin — the li's own box edge, matching a literal reading of "align to the left side of the li item"), with a downward-pointing arrow near that left edge. This is the same orientation as the base `.tooltip::after` bridge default, so no bridge override was needed at this breakpoint — only the desktop override above needed one.
- **Mobile-first structure**: written following this file's existing convention (`@media (min-width: $breakpoint-desktop)` nested inside the base rule, not a separate `max-width` block) — the above/left-aligned/downward-arrow placement is the base (unqualified) rule, and the desktop beside/centered/rightward-arrow placement lives in the nested `min-width` override, requiring explicit `bottom: auto; left: auto;` resets there since an absolutely-positioned element with both `top`/`bottom` (or both `left`/`right`) set and no explicit `height`/`width` will stretch to satisfy both rather than let the later declaration silently win.
- All position/size overrides on `.tooltip.resume-skills__skill-tooltip` (and its `::before`/`::after`) use the compound `.tooltip.` prefix, not just the bare class — same specificity reasoning as the diamond-bullet and sub-item-diamond fixes above: the base `.tooltip`/`.tooltip::before`/`.tooltip::after` rules in Tooltip/index.scss already set several of these same properties (width/height on `::before`, the full box model on `::after`), so a same-specificity override would be a source-order gamble across two different files instead of a guaranteed win.

## Diamond bullets extracted into `_lists.scss` (2026-08-09)

The user pointed out the diamond-bullet `<li>` look wasn't conceptually Skills-specific — other resume sections (Experience, Projects, Education) could plausibly want the same bulleted-list look later — and asked for it to move to common CSS, explicitly excluding the expandable arrow-toggle mechanism (genuinely Skills-only interactive behavior, not a bullet look) and explicitly excluding `Header`'s `<li>`s (already correctly markerless flex rows). Full rationale for the new partial's shape/wiring lives in [LAYOUT-SETUP.md](../LAYOUT-SETUP.md)'s "A fourth shared partial: `_lists.scss`" section; this entry covers only what changed on the `Skills` side.

- **What moved out**: the `dd { ul {...} li {...} &::before {...} } }` block (list reset + diamond marker + position) and its light-theme `color: $grape-press` override — both now live in `src/scss/_lists.scss` as the opt-in `.bullet-list` class, `@use`'d once from `Layout/index.scss`. `dd` itself kept only its own `margin: 0.125rem 0;`.
- **What stayed, now compounded with `.bullet-list`**: the sub-item list's own `margin: 0.25rem 0 0;`/`li { margin: 0.125rem 0; }`, and its diamond's `font-size: 1rem;`/`transition: color ...;` tweaks. Previously these lived nested under `&__sub-list` inside `.resume-skills { }` (BEM concatenation, no ancestor prefix) or as a separately fully-qualified `.resume-skills .resume-skills__group .resume-skills__sub-list li::before` selector; both became one standalone `.bullet-list.resume-skills__sub-list { ... }` rule instead, since `.bullet-list` is now a second class living on the exact same `<ul>` (`Skills/index.tsx`'s sub-list gained `className="bullet-list resume-skills__sub-list"`, and the per-category skill list gained a bare `className="bullet-list"`). The compound form isn't strictly required by any live specificity fight today (the new base `.bullet-list li::before` only sets `content`/position/`color`, and this override only touches `font-size`/`transition`) but was kept anyway, matching this file's established habit of not leaving same-specificity same-selector-shape ties to source order.
- **Re-verified, not reworked**: the expandable-suppression rule (`&__skill.resume-skills__skill--expandable { &::before { content: none; } }`) needed no changes. It was already a 2-class compound selector (`.resume-skills__skill.resume-skills__skill--expandable::before`), which outranks the new 1-class `.bullet-list li::before` base (1 class + 2 elements) on class-count alone, the same margin it previously had over the old `.resume-skills dd li::before` base (1 class + 3 elements) — the win condition didn't change, only which selector it's beating.
- Verified: `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run test:coverage` all clean — no test changes needed, since nothing about roles/text/DOM structure changed, only a `className` addition and a CSS relocation. Visually re-verified via the ad hoc Playwright driver (see `claude-docs/PLAYWRIGHT-ADHOC-VERIFICATION.md`): both lists' diamonds render identically to before in both themes, the expandable arrow's screen/print suppress-restore still works, and `Header`'s lists are visually unchanged.

## Expand-arrow unclickable while its own tooltip is showing (2026-08-10)

Bug report: clicking the ▶ arrow on an expandable skill did nothing, while clicking the label text right next to it worked fine.

- Root cause, found via the ad hoc Playwright driver (`claude-docs/PLAYWRIGHT-ADHOC-VERIFICATION.md`) rather than by reading the CSS alone — a synthetic click landed fine until the repro added a `.hover()` first (the realistic sequence: you have to hover the button to aim for the arrow, which is exactly what shows the "Click for more info" tooltip): at `$breakpoint-desktop` and up, `.tooltip.resume-skills__skill-tooltip`'s hover-persistence bridge (`::after`, see [TOOLTIP.md](TOOLTIP.md)) is positioned relative to the trigger's `<li>` and sized to close the gap back to the li's own left edge. But the toggle button's actual hit box extends _past_ that edge, into the li's bullet gutter (`margin-left: -1.25rem` / `padding-left: 1.25rem`, see the arrow-positioning comment above) — that's exactly where the arrow itself renders. So once hover reveals the tooltip, its bridge sits stacked on top of that gutter sliver of the button (both default to normal stacking, tooltip is later in DOM order and has explicit `z-index: 1`) and swallows clicks there, while the label text (outside the gutter, further right) is untouched and still clickable. Confirmed the visible tooltip body itself never reaches that far — only the invisible bridge does — via `elementFromPoint` at the arrow's coordinates before/after the fix.
- Fix: gave `.resume-skills__skill-toggle` `z-index: 2` (already `position: relative` for its own `::before` arrow), just above the tooltip's `z-index: 1`. Stacking only changes the outcome where the two boxes actually overlap (that gutter sliver) — the visible tooltip content and its dismiss button live entirely outside the toggle's box, so this doesn't affect them or anything else about `Tooltip`. Scoped to `Skills` only; didn't touch the shared `Tooltip` component since the collision is specific to this trigger's unusually-wide hit box, not a general Tooltip bug.
- Verified via the ad hoc Playwright driver: with the tooltip forced open by a real `.hover()` first, clicking the arrow's coordinates now toggles `aria-expanded` as expected; the tooltip's own dismiss (×) button and a plain label-text click were re-checked afterwards and still work. `npm run test:coverage`, `npm run lint`, `npm run typecheck` all clean (CSS-only change, no test updates needed).
