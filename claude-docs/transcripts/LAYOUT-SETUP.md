# Layout Setup — Implementation Record

This document is a transcript of the work done to set up the site's general page layout: the approved plan, and how the actual implementation ended up differing from it after some back-and-forth on font choice.

## Summary

- A shared `Layout` component (`src/components/Layout.tsx`) now wraps both `src/pages/index.tsx` and `src/pages/404.tsx`, replacing each page's own independent markup/styling.
- Screen: outer page background `$wine-dark` (`#110011`) behind a "paper" card, `$silver-oxide` (`#211d28`) — two separate Sass variables (`src/scss/_variables.scss`) so either can be retuned independently. White text (`$text: #fff`), card elevated with `box-shadow` (`0 20px 45px rgba(8, 7, 9, 0.8)`), square corners, `4rem` padding.
- Print (`@media print`): flips to a plain white page (`$print-bg: #fff`) with `$silver-oxide` (`#211d28`) text, no shadow/padding on the card, `page-break-inside: avoid`. `@page { size: 8.5in 11in; margin: 0.5in; }` sizes the printed sheet.
- Typography (`src/scss/_typography.scss`): body text in Lexend, headings in **Bitter** — chosen after several rounds of narrowing down a "modern goth, still corporate" heading font (see below). Currently: `Lexend` at weight `200` for body copy (`p`), `Bitter` at weight `300` for headings (`h1`–`h4`) — both lighter than their initial pass (body 300, headings 400), which itself was a step down from an even heavier first draft (600/700).
- `src/scss/index.scss` (light theme, no print handling, no shared layout) was deleted and replaced by `src/scss/layout.scss` + the two partials above.
- Scope was deliberately narrowed to **shell only** — colors, typography, print rules, page structure — reusing the existing placeholder heading/copy. Real resume content (contact card, experience, education, skills sections) is explicit future work.
- Card background texture and its attribution — see [components/BACKGROUND-CREDIT.md](components/BACKGROUND-CREDIT.md).

## How the font choice diverged from the plan

The plan's first pass proposed `Lora` for headings, paired with the existing Lexend body font, mirroring the old resume's serif/sans split conceptually. Before implementing, the user asked for something "more modern goth, still corporate appropriate" instead, which took a few rounds to converge on:

1. **First round** (serif/display options): `Fraunces`, `Bodoni Moda`, `Big Shoulders Display` were proposed. The user liked the direction of `Big Shoulders Display` (a literal "gothic" grotesque sans) but found it "too blocky" and asked for something more angular.
2. **Second round** (angular sans options): `Space Grotesk`, `Syne`, `Unbounded` were proposed as more angular, less blocky alternatives. The user redirected back to wanting serif options instead.
3. **Third round** (serif options): `Playfair Display`, `Bodoni Moda`, `IBM Plex Serif` were proposed. The user asked for something that mixes `Playfair Display`'s classic drama with `Syne`'s geometric angularity — a serif/sans hybrid brief.
4. **Fourth round**: `Fraunces` (a serif built with an adjustable "wonk" that gives it geometric, angular character alongside high-contrast classic serif structure) and `Besley` (a more structured, geometric slab-serif) were proposed as the closest real matches. The user pushed back once more, describing the goal as "corporate goth" incorporating "the whimsy of Syne and Playfair's classiness" — which is, in substance, the same brief `Fraunces` was proposed for.
5. **Landed on `Fraunces`** — the one Google Font purpose-built to combine a classic high-contrast serif structure with an adjustable "wonk" axis that reads as angular/whimsical rather than blocky, matching the brief directly rather than as a compromise. Implemented and verified in the browser.
6. **Follow-up**: the initial weights chosen (Lexend 400–700, Fraunces 600/700) read too heavy on screen. Both were dropped to lighter weights — Lexend 300/400/500 (body set at 300) and Fraunces 400/500 (headings set at 400) — closer to the old resume's own `font-weight: 300` body text.
7. **Reopened after seeing it rendered**: the user didn't like `Fraunces` in practice and reframed the brief once more — "something like Syne but with serifs," i.e. a _geometric slab serif_ (serifs built with the same squared-off, structural logic as a grotesque sans, rather than classic bracketed serifs) instead of a high-contrast display serif. `Besley`, `Zilla Slab`, and `Bitter` were proposed as slab-serif candidates at that end of the spectrum, ranging from sharp/structural (`Besley`) to warm/irregular (`Zilla Slab`) to clean/neutral (`Bitter`). The user picked **`Bitter`** — the most restrained, corporate-safe of the three. `_typography.scss`'s `@import` and `$font-heading` were swapped from Fraunces to Bitter accordingly.

## Color naming diverged from the plan too

The plan originally used generic names (`$body-bg`, `$card-bg`) for the two background variables. Before implementation, the user requested specific values and names instead: the outer page background became `$wine-dark: #110011`, and the paper card background became `$silver-oxide: #333` (also reused for the print text color, rather than introducing a third name for the same `#333` value). No `$charcoal` or `$chrome` naming was used, per explicit instruction.

## Post-implementation refinement

After the initial implementation landed, styling was tuned further directly in the editor, in a few passes:

- `src/scss/_variables.scss`: `$silver-oxide` moved off its original `#333` — first to `#1d1e28`, then to its current `#211d28` — a cooler dark navy-charcoal rather than a neutral gray. `$shadow` was retuned alongside it, landing at `rgba(8, 7, 9, 0.8)`.
- `src/scss/layout.scss`: card padding became a uniform `4rem` (was `3rem 1.5rem`), and the screen-mode `border-radius` was dropped entirely — the card now has square corners at all times, not just in print.
- `src/scss/_typography.scss`: heading weight dropped from `400` to `300`, body weight from `300` to `200`; body copy (`p`) size/line-height also shifted, from `1.05rem`/`1.6` to `1.2rem`/`1.25` — tighter line spacing at a slightly larger size.

## Splitting component SCSS out of `layout.scss`, per component

Every component's styling had lived together in the single `src/scss/layout.scss`, keyed only by class name (`.paper-card`, `.theme-toggle`, `.tooltip`, `.background-credit`, ...) — fine while there were few components, but it meant editing `ThemeToggle`'s look meant editing a file that also defined `Tooltip`'s and `BackgroundCredit`'s. Per explicit request, each component was moved into its own folder under `src/components/`, with its `.tsx` and `.scss` colocated:

- `src/components/Layout.tsx` → `src/components/Layout/index.tsx` + `src/components/Layout/index.scss` — kept the site-wide bits that aren't any one component's concern: the `*` box-sizing reset, `html`/`body` base colors, `.paper-chrome`/`.paper-card` (+ its `::after` texture overlay, light-theme override, print rules), the `@page` size rule, and the print `html`/`body` override. Also the reduced-motion rules for `.paper-card`/`.paper-card::after` specifically.
- `src/components/ThemeToggle.tsx` → `src/components/ThemeToggle/index.tsx` + `index.scss` — `.theme-toggle` and everything under it (`__facets`, `__facet` + its `--out`/`--pre-enter` modifiers), plus `.theme-toggle-tooltip` and its `__label--to-light`/`--to-dark` modifiers. That tooltip-placement CSS moved here rather than into `Tooltip`'s own folder, since it's this instance's placement, not part of `Tooltip`'s generic look (see [components/TOOLTIP.md](components/TOOLTIP.md)).
- `src/components/Tooltip.tsx` → `src/components/Tooltip/index.tsx` + `index.scss` — just the generic `.tooltip`/`.tooltip-trigger` look (color, fade, shadow, direction-agnostic arrow base), reusable by any future trigger.
- `src/components/BackgroundCredit.tsx` → `src/components/BackgroundCredit/index.tsx` + `index.scss` — just `.background-credit`.
- Each component's `.test.tsx` moved into its folder alongside it too (`ThemeToggle/index.test.tsx`, `Tooltip/index.test.tsx`), importing the sibling module as `from '.'`.
- Every folder's component file is named `index.tsx` (not e.g. `ThemeToggle/ThemeToggle.tsx`) specifically so every existing import site — `Layout` from `src/pages/*`, `ThemeToggle`/`BackgroundCredit` from `Layout`, `Tooltip` from `ThemeToggle` — keeps working unchanged (`from '../components/Layout'` still resolves, now to the folder). Same reasoning for `index.scss` over `ComponentName.scss`, for naming consistency between the two colocated files.
- **Font variables moved out of `_typography.scss` and into `_variables.scss`**: `$font-body`/`$font-heading` used to live in `_typography.scss` alongside the actual global `body`/`h1`–`h4`/`p` CSS rules and the Google Fonts `@import`. `Tooltip/index.scss` needs `$font-body` for its own `font-family` declaration but must not pull in `_typography.scss`'s global tag rules — `gatsby-plugin-sass` compiles each `.scss` file imported from a `.tsx` as its own independent entry point, so `@use`-ing a partial that has actual top-level CSS rules (not just variable definitions) duplicates those rules into every entry point that uses it. Pure variable definitions have no such cost — `@use`-ing `_variables.scss` from every component's `.scss` emits no extra CSS. `_typography.scss` itself now starts with `@use './variables' as *;` to get `$font-body`/`$font-heading` back for its own body/heading rules, and is `@use`'d only from `Layout/index.scss`, the one place that still needs its global tag styling and font `@import`.
- Verified after the move: `npm run typecheck`, `npm run lint`, `npm test` (`test:coverage` still 100% lines/branches/functions/statements — the coverage `include: ['src/**/*.{ts,tsx}']` glob in `vitest.config.ts` picked up the new nested paths with no config change needed, same for `.oxlintrc.json`'s `src/**/*.{ts,tsx}` override and `tsconfig.json`'s `./src/**/*` include), and `npm run build` all pass. Inspected the built CSS to confirm the font-variable move actually avoided duplication: `font-family:Lexend` appears exactly twice in the production stylesheet (the `body` rule and `.tooltip`'s rule), and the Google Fonts `@import` appears exactly once — not once per entry point.

## A third shared partial: `_buttons.scss`

Per explicit request, every `<button>` in the app now shares one base look (fill color, hover/focus/active states, no rounded corners, a "pushed" click effect) instead of each component styling its own button independently. `src/scss/_buttons.scss` joins `_variables.scss`/`_typography.scss` as the third partial in `src/scss/`, following the same rule `_typography.scss` already established: it emits real global CSS (a bare `button { ... }` rule), so it's `@use`'d from exactly one place, `Layout/index.scss`, rather than from every component that happens to render a button — `gatsby-plugin-sass` compiles each component's `.scss` as its own independent entry point, so a partial with actual top-level rules would otherwise get duplicated into every one of them.

The fill color depends on where the button sits, not on light/dark theme: a button inside `.paper-card` defaults to `$wine-dark`; a button anywhere else defaults to `$silver-oxide` (the same two backgrounds those two contexts already use elsewhere in reverse — a button reads as an inverse-contrast chip against whichever surface it's on). Hover/focus turns it `$wine`; a click turns it `$grape-press`, a more-saturated, darker `$wine` derived via Dart Sass's `sass:color` module (`_variables.scss`) rather than hand-picked, so it stays the same hue family as the accent color it's based on. Clicking also gives the button a "pushed" effect — the fill (`::before`, not the button itself) shrinks slightly via `transform: scale(0.97)`, anchored at its own bottom edge (`transform-origin: bottom`) so the bottom stays planted and only the top sinks in, while the button's actual content (icon/text) stays put, unscaled. Both the fill's color fade and its push-shrink reuse the same `$theme-transition-duration`/`$theme-transition-easing` as every other fade in the app, rather than a separate timing.

Mechanically, every button now paints its fill on a `::before` (matching the technique `ThemeToggle` already used for its own reasons — see [components/THEME-TOGGLE.md](components/THEME-TOGGLE.md)), not on the button element directly, so one shared rule works the same way everywhere. This surfaced two non-obvious CSS issues, both fixed in `_buttons.scss` itself: an absolutely-positioned `::before` with `z-index: auto` actually paints _on top of_ the button's own in-flow text per normal painting order (fixed with `z-index: -1` on `::before` plus `position: relative; z-index: 0;` on the button, the same stacking-context pattern `.paper-card`/`::after` already uses above); and excluding `Tooltip`'s dismiss `×` from all of this needed `:not(:where(.tooltip__dismiss))` rather than a plain `:not(.tooltip__dismiss)`, since `:not()`'s specificity equals its argument's while `:where()`'s is always zero — the plain form would have outranked existing single-class overrides like `.theme-toggle`'s own `position: absolute` and stomped the dismiss button's own load-bearing `translateY(-50%)` centering transform. See [components/THEME-TOGGLE.md](components/THEME-TOGGLE.md), [components/RESTORE-TOOLTIPS.md](components/RESTORE-TOOLTIPS.md), and [components/TOOLTIP.md](components/TOOLTIP.md) for how each component's own styling changed (or deliberately didn't) as a result.

## Moving the Google Fonts request out of the SCSS bundle

The user reported font loading was slowing down site load. The culprit was `_typography.scss`'s `@import url('https://fonts.googleapis.com/css2?...')` — a CSS `@import`, which the browser can only discover after it has fetched and parsed the compiled `commons.css` bundle looking for it. That serializes three round trips before text can render in the right font: fetch+parse `commons.css` → discover and request the Google Fonts CSS → parse that and request the actual `.woff2` files from `fonts.gstatic.com`.

Two fixes were on the table: self-host the fonts via `@fontsource/lexend`/`@fontsource/bitter` (eliminates the external requests entirely), or keep Google Fonts but load them non-blocking (still external, but discovered immediately). Asked the user directly; they picked the latter — keep Google Fonts.

Implemented as the standard pattern Google Fonts' own embed UI generates: two `<link rel="preconnect">` (one to `fonts.googleapis.com`, one to `fonts.gstatic.com` with `crossOrigin: 'anonymous'` since that one's a font-file fetch, not same-origin) plus a `<link rel="stylesheet">` with the same URL the old `@import` used (including `display=swap`), all three injected via `gatsby-ssr.ts`'s existing `onRenderBody`/`setHeadComponents` hook (same mechanism already used for the theme-init inline script) rather than staying in the SCSS bundle. `_typography.scss` now only has a comment explaining where the font request moved to and why — no functional CSS change there beyond deleting the `@import` line.

Verified: `npm run typecheck`, `npm run lint`, `npm test` all clean. `npm run build` fails in this sandbox on an unrelated LMDB error that reproduces identically on a clean `main` checkout with no changes at all (pre-existing environment limitation, not a regression). Verified instead via `npm run develop` + a Playwright script: confirmed the compiled `commons.css` no longer contains the `@import`, confirmed the three new `<link>` tags render in `<head>` ahead of `commons.css`, and confirmed `getComputedStyle` on `body`/`h1` still resolves to `Lexend`/`Bitter` respectively (i.e. the fonts still actually load and apply, just via a different request path).

## Replacing Bitter with a more angular heading font

The user felt `Bitter` — the clean/neutral slab serif landed on in the original font search (see above) — wasn't angular enough for the "geometric styling of the design" once seen in practice.

Several rounds of narrowing:

1. **First round** (sharper slab serifs, staying in the same family as Bitter): `Besley` (the sharp/structural alternative already scouted alongside Bitter originally), `Josefin Slab` (slab companion to the geometric `Josefin Sans`), and `Rokkitt` (a bolder, blockier geometric slab) were proposed. The user rejected all three as "still too classic."
2. **Second round** (non-classic-reading serif/slab alternatives): `Big Shoulders Slab` at a lighter weight (revisiting the industrial/gothic direction the user had liked in `Big Shoulders Display` during the original search, minus the blockiness that got it rejected then) and `Unbounded` were offered, alongside the option to drop the serif requirement entirely. The user chose to reopen the search to sans-serif headings altogether.
3. **Third round** (angular geometric sans): `Space Grotesk`, `Syne`, `Unbounded`, and `Chakra Petch` (a new, sharper/cut-corner candidate not previously scouted) were proposed. The user picked `Space Grotesk`.
4. **Reopened after trying `Space Grotesk`**: too narrow. `Syne` (wide and geometric even at its own regular weights, and the same font whose "geometric angularity" was named in the original Bitter-era brief), `Unbounded`, and `Archivo Expanded` were proposed as wider alternatives. The user picked **`Syne`**.

Implemented: `$font-heading` in `src/scss/_variables.scss` changed from `'Bitter', Georgia, serif` to `'Syne', Arial, Helvetica, sans-serif` (serif fallback dropped since Syne is a sans, matching the pattern `$font-body`'s stack already uses). `gatsby-ssr.ts`'s Google Fonts `<link>` swapped `Bitter:wght@300;400;500` for `Syne:wght@400;500;600;700` — Syne's lightest available weight is 400 (no 300 cut exists), so the weight range shifted up rather than keeping the same numbers; `_typography.scss`'s actual `h1`–`h4` rules were mid-edit on this branch independent of the font swap and were left untouched.

Verified: `npm run typecheck` and `npm run lint` both clean. The user visually verified the change themselves rather than having it driven through a dev-server/Playwright check.

## Self-hosting fonts instead of Google Fonts

A mobile PageSpeed Insights run against the deployed site flagged the Google Fonts `<link rel="stylesheet">` as render-blocking (~750ms est. savings) and as the start of a critical request chain (HTML → `fonts.googleapis.com` CSS → two `fonts.gstatic.com` `.woff2` files, ~198ms). This is the same request "Moving the Google Fonts request out of the SCSS bundle" (above) had already made non-blocking-to-discover by moving it into `gatsby-ssr.ts`'s `<link>`s — that fix addressed _discovery_ latency, but the external DNS/connection/CSS/woff2 chain itself was untouched and had now become the largest single item in the report.

That earlier section records the user being asked self-host vs. keep-CDN-non-blocking and picking the CDN. Asked again with this new data in hand, the user picked **self-hosting** this time — the CDN choice is superseded.

While auditing which weights were actually in use before picking what to self-host, only 3 of the 8 requested weights turned out to ever be applied: `Lexend` 200 (the `body` default in `_typography.scss`) and 400 (`Skills/index.scss`'s only override); `Syne` 400 (`_typography.scss`'s only heading rule, unchanged since "Replacing Bitter..." above). `Lexend` 300/500 and `Syne` 500/600/700 were being fetched and never applied — a comment in `_typography.scss` about light mode "compensating back up to the fonts' regular/medium instances" turned out to describe something that was never actually implemented (grepped for `font-weight`/`letter-spacing` across every component's SCSS and the light-mode `data-theme='light'` blocks; nothing sets a heavier weight there).

Implemented: `npm install @fontsource/lexend @fontsource/syne` (added to `dependencies`, since they ship in the production bundle, not just tooling). Created `gatsby-browser.ts` (previously absent — anticipated by `.oxlintrc.json`'s browser override, which already listed it) importing only the three weight files actually used: `@fontsource/lexend/200.css`, `@fontsource/lexend/400.css`, `@fontsource/syne/400.css`. Confirmed each ships `font-display: swap` by default (read the installed CSS directly) — no extra config needed for that. `gatsby-ssr.ts`'s two `preconnect` `<link>`s and the `stylesheet` `<link>` were deleted entirely from `onRenderBody`'s `setHeadComponents`, leaving only the theme-init `<script>`. `_typography.scss`'s top comment was rewritten to describe the current self-hosted setup instead of the old discovery-order rationale for the Google Fonts `<link>`.

Verified: `npm run typecheck`, `npm run lint`, `npm test`/`npm run test:coverage` (including `Seo`'s new tests — see [components/SEO.md](components/SEO.md); coverage stayed at 98.51%/100%/95.23%/100%, well above the 80% threshold) all clean. Font loading was checked via `npm run develop` plus an ad hoc Playwright script (`page.on('request', ...)` to catch any `fonts.googleapis.com`/`fonts.gstatic.com` calls, `getComputedStyle` on `body`/`h1`): title, meta description, and both fonts resolved correctly, zero external font requests fired. Also confirmed via a real `npm run build` (see "Trimming legacy-browser JS via browserslist" below for why this sandbox's usual LMDB limitation didn't block it this time): built `public/index.html` contains the `<meta name="description">` tag and zero occurrences of `fonts.googleapis`/`fonts.gstatic`. `npm run test:e2e:coverage` also passed in full (18/18), with `Seo` itself at 100% coverage across the board.

## Trimming legacy-browser JS via browserslist

The same PageSpeed Insights run also flagged "Reduce unused JavaScript" (Lighthouse's generic bundle-analyzer hint, no specific savings number attached). The user was asked how they wanted this enforced going forward and explicitly ruled out both a CI gate (Lighthouse CI, a `size-limit` budget check) and a one-off manual `npm run analyze` pass — they wanted unused JS stripped automatically as part of every normal build, the way tree-shaking works, with nothing to maintain or enforce.

Investigated by reading `node_modules/babel-preset-gatsby/index.js` directly: it configures `@babel/preset-env` with `useBuiltIns: 'usage'`, `corejs: 3`, and `targets` read from the project's resolved browserslist config. The repo had no `browserslist` field in `package.json` and no `.browserslistrc` at all, so browserslist was falling back to its broad default query (`> 0.5%, last 2 versions, Firefox ESR, not dead`) — still including old/legacy browser targets, which makes Babel inject `core-js` polyfills and downlevel syntax that's simply dead code for any visitor on a modern evergreen browser. This is a real, mechanical source of "unused JavaScript" distinct from ordinary dead-code elimination (which Gatsby's production webpack config already handles via normal tree-shaking).

Implemented: added `.browserslistrc` at the repo root with a single line, `defaults and fully supports es6-module` — the standard "modern browsers only" query (as used in web.dev's guidance on serving modern JS), resolving to current evergreen Chrome/Firefox/Safari/Edge and excluding IE11/legacy Android/Opera Mini (none of which support ES modules). No other change needed — `babel-preset-gatsby` picks this up automatically via `browserslist`'s own resolution, on every `gatsby build`, with no new pipeline step, no CI job, and no manual analyzer run.

Verified: `npx browserslist` confirms the modern target list resolves correctly. Unlike the LMDB failure recorded elsewhere in this transcript, `gatsby build` ran successfully in this sandbox on this occasion (the bug appears intermittent/environment-dependent rather than a hard block), so the fix's actual effect could be measured directly: `npm run clean && npm run build` with `.browserslistrc` removed produced `app-*.js` at 72K; restoring `.browserslistrc` and rebuilding clean dropped it to 60K — a ~17% reduction in first-party app code, consistent with dropped `core-js` polyfills/downleveled syntax for legacy targets. `framework-*.js` (React/ReactDOM's own pre-built bundles) stayed at 188K in both runs, as expected — browserslist only governs Babel's transform of this project's own source, not pre-compiled `node_modules` packages.
