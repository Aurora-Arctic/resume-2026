# Header — Summary

Full implementation history: [claude-docs/transcripts/components/HEADER.md](../transcripts/components/HEADER.md)

- Renders the resume's name/title/contact block from a `HeaderData` prop (typed in `src/data/resume.ts`).
- The person's name is now the page's `<h1>` — replaces the old `<h1>Resume 2026</h1>` site-title heading, matching the conventional resume pattern (name as primary heading, not the site name).
- Contact details render as three separate blocks, each landing on its own line via normal block flow: `location` as a standalone `<p className="resume-header__location">`, then email (`mailto:` link) + phone together in `<ul className="resume-header__contact" aria-label="Contact details">`, then `links` in its own `<ul className="resume-header__links" aria-label="Links">`. The `aria-label`s exist because two adjacent unlabeled `<ul>`s would otherwise be ambiguous to screen readers. At `$breakpoint-desktop` (see [RESUME.md](RESUME.md)) the whole header right-aligns and both lists' wrapped items hug the right edge (`justify-content: flex-end`); below that breakpoint it's left-aligned, unchanged from before. `.resume-header h1` also gets a smaller **fixed** `font-size` (not a second `clamp()`) at that same breakpoint, scoped by selector so the global `h1` rule in `src/scss/_typography.scss` is untouched — sized against the header's ~267px column width once `.paper-card` hits its own 960px cap, so it doesn't wrap to a second line.
- `location`/`email`/`phone` are AES-GCM ciphertext at rest (not plaintext) and only decrypt client-side when the page is loaded with a `?k=` URL key — see [CONTACT-ENCRYPTION.md](../CONTACT-ENCRYPTION.md) for the full scheme. Without a valid key, `location` and the `&__contact` list simply don't render (no ciphertext, no error) — all-or-nothing, decrypted together. `&__links` always renders regardless of key state. `links` anchors carry `rel="noreferrer"` so clicking one from an unlocked page doesn't leak the key via `Referer`.
- The `resume.marwynn.net` link in `header.links` is a stand-in for "this same site" (matched by hostname), not a fixed destination: `resolveLink` rewrites both its `href` and displayed label to `GATSBY_SITE_URL` for whatever environment the build is actually running in — `localhost:8000` in development, `staging.resume.marwynn.net` on staging, `resume.marwynn.net` on main (see `gatsby-config.ts`'s `siteUrl`, `.env.development`/`.env.production`, and `netlify.toml`'s per-context overrides). It's also a deliberate exception to the no-key-leak rule: once a valid `?k=` unlocks this page, that same key is appended to this self-link's resolved `href` (via `URL`/`URLSearchParams`) so a visitor doesn't have to re-supply it when following it back to the site they're already on. Every other link renders its raw `href` unchanged. See [CONTACT-ENCRYPTION.md](../CONTACT-ENCRYPTION.md) for why this doesn't conflict with the `rel="noreferrer"` rationale above.
- First section rendered by `Resume` — see [RESUME.md](RESUME.md) for the overall section-order/data-model/layout rationale shared across all six sections.
