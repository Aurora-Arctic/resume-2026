# Header — Summary

Full implementation history: [claude-docs/transcripts/components/HEADER.md](../transcripts/components/HEADER.md)

- Renders the resume's name/title/contact block from a `HeaderData` prop (typed in `src/data/resume.ts`).
- The person's name is now the page's `<h1>` — replaces the old `<h1>Resume 2026</h1>` site-title heading, matching the conventional resume pattern (name as primary heading, not the site name).
- Title (`data.title`) splits on `" | "` and renders each segment on its own line (a `<br />` between them) inside `.resume-header__title` — a no-op for any title without a `" | "` separator.
- Contact details render as two blocks: email (`mailto:` link), phone (`tel:` link, href built from `contact.phone.replace(/\D/g, '')` — digits only; visible text stays the original formatted string), then location, each its own `<li>` line (in that order) inside a single `<ul className="resume-header__contact" aria-label="Contact details" aria-live="polite">`, always in the DOM (not gated on `contact.email || contact.phone`), empty until contact data decrypts (all three decrypt together, see below); then `links` in its own `<ul className="resume-header__links" aria-label="Links">`. The `aria-live="polite"` is crucial: the region must exist before its content changes for assistive technology to reliably announce decrypted contact info. Both `mailto:` and `tel:` links are exempt from `_print.scss`'s link-URL print reveal (see [LAYOUT-SETUP.md](../LAYOUT-SETUP.md)) since their target is already the visible text. The `aria-label`s exist because two adjacent unlabeled `<ul>`s would otherwise be ambiguous to screen readers. The header stays left-aligned at every width (see [RESUME.md](RESUME.md) for why the desktop right-align was reverted). `.resume-header h1` no longer overrides `font-size` at `$breakpoint-desktop`/print either — it uses the global `h1` `clamp()` from `src/scss/_typography.scss` at every width now that the fixed-size override (which existed only to keep the name from wrapping in the narrow right-hand column) no longer applies.
- `location`/`email`/`phone` are AES-GCM ciphertext at rest (not plaintext) and only decrypt client-side when the page is loaded with a `?k=` URL key — see [CONTACT-ENCRYPTION.md](../CONTACT-ENCRYPTION.md) for the full scheme. Without a valid key, the whole `&__contact` list simply doesn't render (no ciphertext, no error) — all-or-nothing, decrypted together. `&__links` always renders regardless of key state. `links` anchors carry `rel="noreferrer"` so clicking one from an unlocked page doesn't leak the key via `Referer`.
- The `resume.marwynn.net` link in `header.links` is a stand-in for "this same site" (matched by hostname), not a fixed destination: `resolveLink` rewrites both its `href` and displayed label to `GATSBY_SITE_URL` for whatever environment the build is actually running in — `localhost:8000` in development, `staging.resume.marwynn.net` on staging, `resume.marwynn.net` on main (see `gatsby-config.ts`'s `siteUrl`, `.env.development`/`.env.production`, and `netlify.toml`'s per-context overrides). It's also a deliberate exception to the no-key-leak rule: once a valid `?k=` unlocks this page, that same key is appended to this self-link's resolved `href` (via `URL`/`URLSearchParams`) so a visitor doesn't have to re-supply it when following it back to the site they're already on. Every other link renders its raw `href` unchanged. See [CONTACT-ENCRYPTION.md](../CONTACT-ENCRYPTION.md) for why this doesn't conflict with the `rel="noreferrer"` rationale above.
- `&__links` renders each entry's _icon_, not its label text: `LinkedinIcon` (FontAwesome's bare "in" mark, not the boxed logo), `GithubIcon` (imported from the shared `GithubIcon` component), and `LinkIcon` (the own-domain entry, plus a fallback for any unrecognized host) — `LinkedinIcon` and `LinkIcon` are hand-transcribed inline SVGs; `GithubIcon` is a reusable component. All use `fill="currentColor"`, following the `@fortawesome/fontawesome-free`-as-devDependency-only convention `PrintOptions`'s `PrintIcon` and `ThemeToggle` established. All three icon components accept a required `className` prop, applied at the call site (e.g. `resume-header__link-icon`), decoupling icon markup from styling. `getLinkIcon(originalHref)`, next to `resolveLink`, picks the icon by matching the **original** (pre-`resolveLink`) href's hostname against `OWN_DOMAIN_HOSTNAME`/`linkedin.com`/`github.com` — the resolved own-domain hostname varies per environment, so icon selection can't read it directly. Each anchor keeps `resolved.label` as its accessible name via an explicit `aria-label` (not supplied by `Tooltip`, which only wires `aria-describedby`) and shows it on hover/focus via a `Tooltip` (one instance per link, each `<li>` its own `position: relative` positioning context, placement class `.resume-header-link-tooltip`). In the Application print tier, `&__links` switches to `flex-direction: column` (via `linear-print-tiers`) so the icons print one per line, top to bottom, like `&__contact`, instead of the wrapped row used elsewhere; in the same tier, link icons are forced to `$print-text` (dark gray) instead of wine, suitable for ATS submissions without color.
- First section rendered by `Resume` — see [RESUME.md](RESUME.md) for the overall section-order/data-model/layout rationale shared across all six sections.
