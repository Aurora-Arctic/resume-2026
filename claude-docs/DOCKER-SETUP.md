# Docker / Dev Container — Summary

Full implementation history: [claude-docs/transcripts/DOCKER-SETUP.md](transcripts/DOCKER-SETUP.md)

- `makefile` wraps Docker Compose (`make docker-build|up|down|rebuild|logs`, targeting `Docker/docker-compose.yaml`) and mirrors the npm scripts one-to-one (`make npm-install|develop|build`, etc.).
- Two Compose services build from `Docker/Dockerfile.node` (multi-stage): `development` (`npm run develop -- --host 0.0.0.0`) and `devcontainer` (VS Code Dev Containers, runs as the `node` user). A `testing` stage in between bakes in headless-Playwright/Chromium deps for CI and local e2e — see [DEV-CONTAINER.md](DEV-CONTAINER.md) for sandbox-specific gotchas when working inside it.
- Both services bind-mount the repo root to `/app` and use a per-service named `node_modules_development`/`node_modules_devcontainer` volume — don't remove it, it prevents host-installed `node_modules` clashing with container-built native deps, and keeps the two containers' `node_modules` from being mutated out from under each other. `builder`'s `npm i` runs as `node`, not root; an `EACCES` on `node_modules` in the devcontainer means the volume is stale from before that fix — recreate it (`docker compose down -v`) rather than re-patching the Dockerfile.
- Both services also mount a per-service named `gatsby_cache_development`/`gatsby_cache_devcontainer` volume directly at `/app/.cache` — works around unreliable LMDB file-locking on the bind-mounted repo root, and fully isolates each service's cache (not just LMDB) from the other. Because `gatsby clean`'s own `fs.remove('.cache')` can't `rmdir` a mount point, `npm run clean` runs `Docker/clean.js` instead, which empties `.cache`'s contents by hand when `CONTAINER_CACHE_DIR` is set and falls straight through to the real `gatsby clean` otherwise (bare-metal `npm run develop`/`build`/`clean` are unaffected). See the transcript for the earlier design (symlinking only `.cache/caches-lmdb`) and why it didn't fully solve cross-container isolation.
- Both services likewise mount a per-service named `gatsby_public_development`/`gatsby_public_devcontainer` volume at `/gatsby-public`, which `Docker/link-public.js` symlinks the whole `public` directory into (same `ensure`/`reset` hooks, no-ops when `CONTAINER_PUBLIC_DIR` is unset) — keeps each container's build output isolated, so a `gatsby clean` (e.g. from `npm run test:e2e:coverage`) in one container can't delete `public` out from under the other. Unlike the cache case, `public` itself is the symlink rather than a nested subdirectory — see the transcript for why that's safe here but wasn't for `.cache`.
- Requires recreating the container (`docker compose down`/`up`, or `make docker-rebuild`) after any of these was added — a running container from before won't have the volume mounted, and `docker compose down -v` clears any now-orphaned `node_modules`/`gatsby_cache`/`gatsby_public` volume from an earlier iteration.
- `devcontainer` passes through `CLAUDE_CODE_OAUTH_TOKEN` (from git-ignored `Docker/.env`) so the Claude Code CLI is pre-authenticated; `make docker-up`/`docker-rebuild` regenerate it via `Docker/update-token.sh`.
- `devcontainer` also bind-mounts git-ignored `Docker/claude-home` to `/home/node/.claude` — a bind mount, not a named volume, deliberately, so it survives `docker compose down -v`. Create it yourself (`mkdir Docker/claude-home`) if missing, to avoid Compose auto-creating it root-owned.
