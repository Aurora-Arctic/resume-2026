# Contact Encryption — Summary

Full implementation history: [claude-docs/transcripts/CONTACT-ENCRYPTION.md](transcripts/CONTACT-ENCRYPTION.md)

- The site is fully static with no backend, so `HeaderData.location`/`.email`/`.phone` (`src/data/resume.ts`) are stored as AES-256-GCM ciphertext rather than plaintext, to deter scrapers that regex-scan the built HTML/JS for contact info. **This is scraper deterrence, not real confidentiality** — the ciphertext and decrypt algorithm both ship in the public bundle, so anyone who obtains a valid `?k=` link (or brute-forces the key) can read the plaintext.
- `src/utils/crypto.ts`: isomorphic helper (`generateKey`/`encryptText`/`decryptText`) built on Web Crypto (`crypto.subtle`), used by both the browser and a Node CLI. The key argument is any string, SHA-256'd into a fixed 256-bit AES key; each encryption uses a random 12-byte IV, output as `base64url(iv || ciphertext || authTag)`. AES-GCM is authenticated, so a wrong/missing key fails decryption cleanly (a rejected promise) instead of producing garbled output.
- **Symmetric — one key, not two**: the same key value both encrypts (offline) and decrypts (client-side via the URL). `npm run generate:key` prints a fresh one; nothing generates or needs a separate "decryption key".
- `scripts/generate-key.ts` / `scripts/encrypt-value.ts` (run via `npm run generate:key` / `npm run encrypt:value -- "<text>" [key]`) import directly from `src/utils/crypto.ts` — no duplicated algorithm. They run under plain `node` (not `ts-node` — see the transcript for why), scoped to ESM via `scripts/package.json`.
- `src/components/Header/index.tsx` decrypts client-side only: a `useEffect` reads `k` from `window.location.search`, decrypts all three fields together, and renders each only on success. No key (or a wrong one) renders none of them — never ciphertext, never a thrown error. SSR/SSG output therefore never contains the plaintext.
- The Header's own outbound `links` (LinkedIn/GitHub/etc.) get `rel="noreferrer"` — without it, clicking one from an unlocked (`?k=...`) page would leak the key to the destination site via the `Referer` header.
- **One deliberate exception**: the `resume.marwynn.net` entry in `header.links` is a self-link, not an external destination — `netlify.toml` redirects the old `marwynn.net`/`www.marwynn.net` domains to `resume.marwynn.net`, this site's own production domain. `Header/index.tsx`'s `resolveLink` (matched by hostname) rewrites it to `GATSBY_SITE_URL` for whichever environment is actually running (`localhost:8000` dev, `staging.resume.marwynn.net` staging, `resume.marwynn.net` main — see `gatsby-config.ts`, `.env.development`/`.env.production`, `netlify.toml`'s per-context overrides) and, uniquely among links, appends the unlocked page's `k` value to that resolved `href` on purpose. Since it always points back at this same site, propagating the key there is intended rather than a leak. This is a different mechanism from the `Referer`-leak `rel="noreferrer"` guards against (an implicit, automatic browser header versus an explicit query param this code adds itself) — `rel="noreferrer"` stays on this link too, since it still blocks the `Referer` header regardless.
- **The real key must never be committed to the repo — not even as a test fixture.** Once `resumeData.header` holds real (not placeholder) ciphertext, the key that decrypts it is a genuine secret: this repo is public, and a key sitting in a `git`-tracked file is no different from the plaintext itself. `e2e/contact-encryption.spec.ts` is built around this constraint — see below.
- Testing: `src/utils/crypto.test.ts` unit-tests the round-trip/wrong-key/random-IV behavior directly (deterministic, no timing concerns) using a throwaway in-memory key. `src/components/Header/index.test.tsx` covers the no-key/valid-key/wrong-key render paths for all three fields with its own throwaway key/fixture (jsdom doesn't implement `crypto.subtle` — see `vitest.setup.ts`'s polyfill, same pattern as its existing `localStorage` one). `e2e/contact-encryption.spec.ts` runs against the real built site but never hardcodes the real key: the no-key/wrong-key cases assert structurally (the contact list has exactly one `<li>` — the static `links` entry — when nothing decrypted), and the successful-decrypt case reads an optional `RESUME_CONTACT_KEY` env var, skipping itself (not failing) when it's unset, e.g. in CI.
