# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A personal resume site (`resume-2026`) built with Gatsby 5, React 18, and TypeScript. Fully static — no backend, database, or state management.

## Commands

- `npm install` — install dependencies
- `npm run develop` — start the dev server at `http://localhost:8000` (hot reload)
- `npm run build` — production build (outputs to `public/`)
- `npm run serve` — serve the production build locally
- `npm run clean` — clear Gatsby's `.cache` and `public` output directories
- `npm run typecheck` — `tsc --noEmit`; `tsconfig.json` has `noEmit: true` so this is the only way to surface type errors (Oxlint's `typescript` plugin is non-type-checked)
- `npm run lint` — Oxlint over the whole project (`npm run lint:fix` to auto-fix)
- `npm run format` — Prettier write over the whole project (`npm run format:check` for CI-style check without writing)
- `npm test` — run unit/component tests once (Vitest, `npm run test:watch` for watch mode)
- `npm run test:e2e` — run Playwright e2e specs (builds and serves the site first; run `npx playwright install` once to fetch browsers — not needed in the `testing`/`devcontainer` Docker images, which bake the chromium binary in)
- `npm run pre-commit` — manually run the same checks the pre-commit hook runs (`lint`, `format:check`, `typecheck`, in that order), without having to make a commit

## Linting & Formatting

- **Oxlint**: `.oxlintrc.json`. Rust-based, no Babel/type-info dependency — replaced ESLint (`eslint.config.mjs`) for speed. Uses oxlint's own default plugin set (`eslint`, `typescript`, `unicorn`, `oxc`) plus `react` (incl. hooks rules — oxlint bundles `eslint-plugin-react-hooks`'s rules into the `react` plugin, no separate package) and `jsx-a11y`, both added on top of the defaults. `settings.react.version` is pinned to the installed React version (oxlint doesn't support `"detect"` the way `eslint-plugin-react` did — passing it throws a config parse error). `overrides` split env globals by execution context the same way the old config did: Node for `gatsby-config.ts`/`gatsby-node.ts`/`gatsby-ssr.ts`/`vitest.config.ts`/`playwright.config.ts`/`e2e/**` (these run at build/test time, not in the browser — `gatsby-ssr.ts` is easy to mistake for client-side code but it isn't), browser for `src/**` and `gatsby-browser.ts`. No `eslint-config-prettier`-equivalent is needed — oxlint doesn't ship the kind of low-level formatting rules that would fight Prettier, so there's nothing to turn off.
- **Prettier**: `.prettierrc` (single quotes, trailing commas, 100-char width, LF endings) + `.prettierignore` (`node_modules`, `public`, `.cache`, `package-lock.json`). No plugins — built-in support covers all file types in this repo (`.ts`/`.tsx`/`.scss`/`.json`/`.md`).
- **Pre-commit hook**: the `pre-commit` npm package (devDependency) reads the `"pre-commit"` array in `package.json` (`["lint", "format:check", "typecheck"]`) and runs those `npm run` scripts before each commit, blocking it on failure. Its `install.js` install script writes `.git/hooks/pre-commit` as part of `npm install` — this is why `pre-commit` needs an approved install script (`allowScripts` in `package.json`) in this sandboxed environment, and why the hook only exists once `npm install` has actually run against a real `.git` directory (i.e. inside the `devcontainer` service against the bind-mounted repo — not during the Docker image build, which only has `package.json`/`package-lock.json` copied in, no `.git`). `npm run pre-commit` (`scripts.pre-commit`, a separate key from the top-level `"pre-commit"` array config) runs the same three checks manually, in the same order, without needing a commit to trigger them — keep the two in sync if the hook's check list changes.

## Testing

- **Unit/component tests**: Vitest (`vitest.config.ts`, `environment: 'jsdom'`, `@vitejs/plugin-react` for the automatic JSX runtime) + React Testing Library. Tests are co-located under `src/` (e.g. `src/pages/index.test.tsx`) — this is deliberate, not just convention: it means they're already covered by tsconfig's `./src/**/*` include and by `.oxlintrc.json`'s `src/**/*.{ts,tsx}` override (jsdom stands in for the browser environment), so no separate config was needed for them. `vitest.config.ts`'s `test.include` is scoped to `src/**/*.test.{ts,tsx}` so discovery doesn't wander into the bind-mounted `Docker/claude-home` plugin cache. `vitest.setup.ts` (`test.setupFiles`) registers RTL's `afterEach(cleanup)` (not automatic, since `test.globals` isn't set) and polyfills `window.localStorage` with an in-memory `Storage` — Node's own native `localStorage` global shadows jsdom's working one once Vitest merges jsdom's `window` into global scope, so components that touch `localStorage` (e.g. `ThemeToggle`) would otherwise fail under test only.
- **Integration/e2e tests**: Playwright (`playwright.config.ts`), specs live in the root-level `e2e/` directory. Since the site is fully static, Playwright's `webServer` builds and serves it (`npm run build && npm run serve`) before running against `http://localhost:8000`. `e2e/` runs under Node (Playwright drives an external browser rather than running in it), so it's deliberately kept out of the browser override — see the Node `overrides` entry in `.oxlintrc.json` and the explicit `tsconfig.json` include entries for `playwright.config.ts`/`vitest.config.ts`/`e2e/**/*`.
- Both frameworks use explicit imports (`import { describe, it, expect } from 'vitest'`, `import { test, expect } from '@playwright/test'`) rather than injected test globals, so no lint-config globals block was needed for the test APIs themselves.

## Docker / Dev Container

- `makefile` wraps Docker Compose: `make docker-build`, `make docker-up`, `make docker-down`, `make docker-rebuild`, `make docker-logs` (all target `Docker/docker-compose.yaml`). It also has `npm-*` targets (`make npm-install`, `make npm-develop`, `make npm-build`, etc.) that wrap the `npm` scripts below one-to-one — both sets of targets are prefixed (`docker-`/`npm-`) so `make build` doesn't have to mean either the Docker image or the Gatsby production build.
- Two Compose services build from `Docker/Dockerfile.node` (multi-stage, `node:24.18.1`):
  - `development` (target `builder`) — runs `npm run develop -- --host 0.0.0.0`, maps port 8000.
  - `devcontainer` (target `devcontainer`) — used interactively via VS Code Dev Containers (`.devcontainer/devcontainer.json`, service `devcontainer`, port 8000 forwarded, runs as `node` user).
- `Dockerfile.node` has a `testing` stage between `builder` and `devcontainer` that installs the shared libs headless Playwright browsers need (`libnspr4`, `libnss3`, etc. — see `npx playwright install-deps`'s own list) and then runs `npx playwright install chromium` to fetch the browser binary itself — chromium only, matching the sole project defined in `playwright.config.ts`. `devcontainer` builds `FROM testing`, so it inherits the libs and browser binary plus its own zsh/oh-my-zsh + dev tools on top. `testing` exists as its own stage so something like CI could target it directly to run `npm run test:e2e` standalone, with no setup step, and without the devcontainer's interactive tooling. Since the binary is baked into the image, only `npm install` populating the named `node_modules` volume remains a one-time-per-volume step (see below) — `npx playwright install` is no longer needed for these images, only for running e2e tests outside of them.
- Both services bind-mount the repo root to `/app` and use a **named `node_modules` volume** — this keeps host-installed `node_modules` from clashing with container-built native deps. Don't remove this volume mapping without understanding why it's there (see commit "Fixed dev container mounting").
- `Dockerfile.node`'s `builder` stage runs `npm i` as the `node` user (via `USER node` before the install), not root — this was fixed after root-owned `npm i` output baked root-owned `node_modules` into the image/volume, breaking `npm install` for anyone working as `node` (the devcontainer's default user) afterward. If you ever see `EACCES` on `node_modules` in the devcontainer, the named volume itself is stale from before this fix — recreate it (`docker compose down -v`, then rebuild) rather than re-patching the Dockerfile.
- The `devcontainer` service passes through `CLAUDE_CODE_OAUTH_TOKEN` so the Claude Code CLI is pre-authenticated on start, sourced from `Docker/.env` (git-ignored — see `Docker/.env.example`). This exists because normal `/login` credentials are stored differently per host OS (a plain file on Linux, but the encrypted Keychain on macOS), so a bind-mounted credentials file only works for Linux hosts; a long-lived token generated via `claude setup-token` on the host works everywhere. `docker compose`'s default project directory is wherever the compose file lives, so the `.env` file must be at `Docker/.env`, not the repo root.
- `make docker-up` and `make docker-rebuild` depend on the `docker-update-token` target, which runs `Docker/update-token.sh` before Docker starts. That script runs `claude setup-token` (an interactive browser OAuth login) on the host every time, extracts the printed `sk-ant-oat...` token, and upserts `CLAUDE_CODE_OAUTH_TOKEN` in `Docker/.env` — so the token is always freshly regenerated before the containers come up. `make docker-build`/`docker-down`/`docker-logs` don't trigger it, since they don't start the `devcontainer` service.
- `devcontainer` also mounts `Docker/claude-home` (git-ignored) on the host to `/home/node/.claude` in the container (Claude Code's config, plugin marketplaces/installs, session history, etc.), not shared with `development` since only `devcontainer` runs the Claude Code CLI (only it gets `CLAUDE_CODE_OAUTH_TOKEN`). This is a **bind mount, not a named Docker volume**, deliberately: `make docker-rebuild` runs `docker compose down -v`, which deletes named volumes — a named `claude-home` volume was tried first and got wiped by exactly that, which is why `Docker/claude-home-backup.tar.gz` (also git-ignored) exists as a one-time manual backup taken to migrate the lost state into the bind-mounted directory. A bind mount isn't touched by `-v`, so it survives rebuilds the same way the repo bind mount (`..:/app`) does. It relies on the same host-uid-1000-matches-container-node-uid assumption as that mount — nothing pre-creates or `chown`s `/home/node/.claude` in `Dockerfile.node` anymore, so if `Docker/claude-home` doesn't already exist on the host, Compose will auto-create it (root-owned on a Linux host), reintroducing the root-ownership pitfall documented for `node_modules` above; create it yourself first (`mkdir Docker/claude-home`) if it isn't already there.
- `.claude/settings.json` at the repo root (git-tracked, so it's present regardless of `~/.claude` state) declares `extraKnownMarketplaces` + `enabledPlugins` for the `cnaught-plugins` marketplace and its `carbonlog` plugin — Claude Code reads project settings on startup and auto-installs anything declared there that isn't already present. With the `Docker/claude-home` bind mount above, that only actually fires the first time (an empty `Docker/claude-home`) — unlike the old named volume, it's not re-triggered by `docker compose down -v`, since `-v` no longer touches this directory at all; it exists as the mechanism that makes plugin state reproducible from a clean `Docker/claude-home` rather than something to reinstall on every rebuild. The `statusLine` command (in the untracked, machine-local `~/.claude/settings.json`, not the repo) deliberately stays out of the project file — it points at a version-pinned path under `~/.claude/plugins/cache/<version>/`, which only exists after that install actually runs.

## Continuous Integration

- GitHub Actions, `.github/workflows/`. Two phase workflows, each composed from small reusable workflows (`workflow_call`) under `.github/workflows/` — `lint.yml`, `format.yml`, `typecheck.yml`, `vitest.yml`, `build.yml`, `playwright.yml`, `audit.yml` — so each check is defined once and shared across phases rather than duplicated per-phase.
  - **`pr-gate.yml`** (`pull_request` → `main`): format check (always), plus lint, typecheck, Vitest, build, Playwright e2e, and a non-blocking `npm audit` (each path-filtered — see below) that posts/updates a single PR comment (not a new comment per run).
  - **`merge-queue.yml`** (`merge_group`): the same six blocking checks as `pr-gate` (including Playwright e2e — deliberately re-run here too, right before merge, since the merge queue can include commits from other PRs merged since `pr-gate` last ran). No `audit` here; that's PR-only.
  - There's intentionally no push-to-`main` workflow — `merge-queue` already re-verifies everything (including e2e) immediately before a commit lands, so a post-merge run would just duplicate that coverage.
  - **Enabling the merge queue is a manual, one-time repo setting** — a workflow listening for `merge_group` does nothing until "Require merge queue" is turned on for `main` in Settings → Branches → branch protection. Without it, `merge-queue.yml` never triggers.
- **Concurrency** (`pr-gate.yml` only): `lint`, `format`, `typecheck`, `vitest`, `build`, `playwright`, and `audit` each have their own job-level `concurrency` group (`pr-gate-<job>-<pr-number>`, `cancel-in-progress: true`), so a new push to the PR cancels only that job's own stale run rather than the whole workflow. `build-image` deliberately gets `cancel-in-progress: false` instead of a cancelling group — it pushes to a shared, content-addressed GHCR tag and GHA layer cache (`cache-to: type=gha,mode=max`), and killing that job mid-push can freeze a half-written layer (e.g. a native binding download cut short) into a cache/tag that every later run with the same Dockerfile/lockfile hash would then keep reusing — corruption that doesn't self-heal on retry. (A prior version put `cancel-in-progress: true` at the whole-workflow level, which hit exactly this bug — surfaced as oxlint's native binding going missing in CI.) `merge-queue.yml` has no concurrency config; `merge_group` runs aren't superseded by new pushes the way `pull_request` runs are.
- **Path filtering** (`pr-gate.yml` only): a `changes` job runs [`dorny/paths-filter`](https://github.com/dorny/paths-filter) against the PR diff and computes a per-check true/false output for `lint`, `typecheck`, `vitest`, `build`, `playwright`, and `audit`, so e.g. a docs-only PR skips all six instead of paying for a full run. `format` is deliberately left ungated — Prettier covers `.md`/`.json` too, so "did formatting change" should run on every push regardless of what changed, not be filtered. Each job's filter list also includes that job's own reusable workflow file plus `pr-gate.yml` and `.github/actions/**`, so editing the check's workflow (or a shared composite action) always reruns it rather than silently going unverified. `build-image` stays unconditional — `format` always needs its `image` output, and the job is already a cheap no-op read in the common case (see below). `merge-queue.yml` deliberately has no path filtering — it already exists to re-verify everything right before merge regardless of what a single PR touched (see above), and filtering off a diff base that can span multiple squashed PRs risks skipping a check a later commit actually needs.
  - The `changes` output is threaded into each of those six jobs as a `should-run` workflow_call input (each reusable workflow's own steps are gated on `inputs.should-run`, defaulting to `true` so merge-queue's unfiltered calls run in full) rather than a job-level `if:` on the calling job in `pr-gate.yml`. `lint`, `typecheck`, `vitest`, `build`, `playwright`, and `build-image`/`format` (always-on) are required status checks in branch protection, registered under the name GitHub gives a job inside a called reusable workflow (`"<job> / <job>"`, e.g. `lint / lint`) — and required for the merge queue too. A job-level `if:` that skips the _calling_ job reports the check under a different, bare name instead (`lint` instead of `lint / lint`), which never satisfies the real required-check name and leaves the PR stuck forever waiting on a check that will never arrive. Keeping the job always-on and skipping its work internally keeps the reported check name identical whether or not the work actually ran. `audit` gets the same `should-run` treatment purely for check-name consistency in the Actions UI — it isn't a required status check itself (see below).
- **Execution environment**: every check runs inside the existing `testing` stage of `Docker/Dockerfile.node` (see Docker section above) via each job's `container:` key, not on the bare runner — this is the same image/stage used for local e2e testing, so CI and local Playwright runs behave identically. `.github/workflows/build-image.yml` builds/pushes that stage to GHCR under a tag derived from `hashFiles('Docker/Dockerfile.node', 'package-lock.json')` and is called first by both phase workflows. Before building, it checks via `docker buildx imagetools inspect` whether that tag already exists and skips the build/push entirely if so — the common case, since most pushes touch neither input — so the job is a fast, side-effect-free read unless a genuine Dockerfile/lockfile change actually forces a rebuild; that read/build split is also what makes the `cancel-in-progress: false` queue above cheap in practice, since there's usually nothing running to queue behind.
- **Naming**: every workflow file has a short comment block directly under its top-level `name:` explaining trigger/purpose/role in the pipeline (workflow YAML has no `description:` schema key — only composite/reusable actions do — so a leading comment is the only place to put this). Names are Title Case (`PR Gate`, `Format Check`, `Playwright E2E`, etc.) except single-word names, which are unaffected either way. `build-image.yml`'s own job id is `build-image` (not the generic `build` it started as), to avoid colliding with `build.yml`'s `build` job in the Actions UI (both used to render as "<workflow name> / build").
- **PR comments**: every comment (`lint`, `format`, `typecheck`, `vitest`, `playwright`, `audit`) opens with a GitHub alert-style callout instead of a plain heading — `> [!NOTE]` + ✅ for a pass, `> [!CAUTION]` + ❌ for a lint/format/typecheck/vitest/playwright failure (these gate the PR), `> [!WARNING]` + ⚠️ for `audit` findings specifically (never `[!CAUTION]` there — `npm audit` is explicitly non-blocking, so it shouldn't read as urgent the way an actual gate failure does). The callout line carries a short stat (e.g. "3 errors, 1 warning across 2 files", "10 passed, 2 failed", "found 40 vulnerabilities"), the commit's short SHA, job duration, and a link to the full Actions run. Below that, a per-check `details` block (only present on failure/findings) gives a nicely formatted, capped breakdown instead of just a raw log dump:
  - `lint`/`typecheck`: a collapsible `<details><summary>Issues</summary>` list of `file:line:col — message` entries, parsed straight from the tool's own default output (neither oxlint nor `tsc --noEmit` prints its own summary line, so counts/entries are derived by grep/regex over the captured log — see the "Summarize output" step in `lint.yml`/`typecheck.yml`).
  - `format`: a collapsible list of the specific non-conforming file paths (Prettier's `--check` output doesn't give per-line detail, just filenames).
  - `vitest`/`playwright`: a collapsible `<details><summary>Failing tests</summary>` list of `` `file` › test title — error message ``, built from each tool's **JSON reporter** (`--reporter=default --reporter=json` for Vitest; `--reporter=list,json,html` for Playwright, output paths set via `--outputFile`/`PLAYWRIGHT_JSON_OUTPUT_NAME`) rather than log-scraping, since both already emit structured pass/fail data — parsed by `.github/scripts/summarize-vitest.mjs` and `summarize-playwright.mjs` (Playwright's JSON nests suites recursively and its error messages carry raw ANSI codes that get stripped before display). Adding `html` to Playwright's reporter list was also a real fix, not just polish — `playwright.yml`'s "Upload Playwright report" artifact step had been uploading an empty `playwright-report/` all along, since no reporter that writes it was ever configured.
  - `audit`: a severity-count table (all 5 severities always shown, even at 0) plus a collapsible, severity-sorted vulnerable-package table (name, severity, whether `npm audit`'s `fixAvailable` is `Yes`/`No`/`Yes (pkg@version, major)`), built from the full `npm audit --json` output rather than just the aggregate counts.
  - Every check's failure `details` is capped (15 entries for lint/format/typecheck/vitest/playwright, 20 rows for audit's package table) with a "_…and N more_" note when truncated — the existing raw-log `<details><summary>Output</summary>` (last 100 lines) stays below it as a fallback for full context.
  - `lint`/`format`/`typecheck` additionally take a `merge-queue` boolean input (default `false`) that switches success/failure comment behavior: from `pr-gate` (`false`) they comment only on failure and minimize (`minimizeComment`/`unminimizeComment` GraphQL mutations) that comment on a later success; `vitest`/`playwright` always comment with the current result. From `merge-queue` (`true`, set on all five `pr-comment`-based calls), every check comments only on failure, on a separate marker/thread (e.g. `<!-- ci-vitest-mergequeue -->` vs `<!-- ci-vitest -->`) so a merge-queue failure is never confused with a `pr-gate` comment for the same check. `audit` has no merge-queue variant — it's PR-only and always updates/creates the same comment, no minimize logic.
  - The callout/meta/summary/details rendering above (for the five checks that share it) is implemented once in the local composite action `.github/actions/pr-comment/` (inputs: `check-name`, `marker-slug`, `success-mode: minimize|comment`, `summary`, `details`, `duration`) — not duplicated as inline `actions/github-script` blocks. `audit.yml` is architecturally different (own inline `actions/github-script` step, no minimize/merge-queue distinction) and builds its own callout/table markdown directly, deliberately not routed through `pr-comment`.
- Since `container:` jobs fix `GITHUB_WORKSPACE` at `/github/workspace` (not `/app`), every job workflow checks out and copies that checkout into `/app` via the local composite action `.github/actions/checkout-to-app/` (`actions/checkout@v4` + `cp -a "$GITHUB_WORKSPACE"/. /app/`) before running its command — `/app` already has `node_modules` from the image's own `npm i` at build time, so nothing needs to reinstall. Used by all seven job workflows (`build-image.yml` excluded — it doesn't run inside the `testing` image itself, since it's what builds that image).
- `lint`, `format`, `typecheck`, `vitest`, `playwright`, and `audit` also share a local composite action, `.github/actions/job-summary/`, for the `$GITHUB_STEP_SUMMARY` write — same callout/summary/details shape as `pr-comment` above, minus the run link (the summary page is already the run page) and minus any marker/upsert logic (each run's summary is fresh, nothing to update in place).
- **Duration**: every check (including `audit`) times its own run via two more local composite actions, `.github/actions/timer-start/` (records epoch seconds) and `.github/actions/timer-elapsed/` (formats the elapsed time as `Ns`/`Mm Ss` from a `timer-start` output) — split into two actions, not one, because a single composite action's steps run as one atomic block and can't span before/after another step in between.
- **Dependabot**: `.github/dependabot.yml` — weekly PRs for `npm` dependencies, `github-actions` versions, and the `docker` base image pin in `Dockerfile.node`.

### Local CI testing with `act`

The real job workflows (`lint.yml`, `format.yml`, `typecheck.yml`, `vitest.yml`, `build.yml`, `playwright.yml`) can be run locally, before pushing, via [`nektos/act`](https://github.com/nektos/act) — host-level only (not devcontainer-integrated; every job's `container:` key means act's job containers become siblings on the host daemon rather than nested inside the devcontainer if run from there, breaking bind-mounted paths). `make act-lint`, `act-format`, `act-typecheck`, `act-vitest`, `act-build`, `act-playwright`, and `act-test` (all six, stopping at the first failure) wrap the underlying `act` invocations — see the makefile's `act-*` section. `audit.yml` and `build-image.yml` are deliberately not covered (`audit.yml`'s comment step can't be skipped without editing the file; `build-image.yml` pushes to GHCR, which has no reason to happen from a laptop). Two real, previously-undiscovered bugs were found this way and fixed in the actual job files, not just worked around locally: local composite actions need act's `--bind` flag (a documented act limitation, not a bug in this repo), and `container:` jobs default to `sh`, not `bash` — GitHub's own documented behavior — so `set -o pipefail` needed explicit `shell: bash` in five job files' `defaults.run`. Full write-up, including the `playwright.yml`-specific workarounds (a seeded action cache, an overridable `PORT`) and why `audit`/`build-image` are excluded: [CI-SETUP.md](CI-SETUP.md#local-ci-testing-with-act).

## Architecture

- **Routing**: Gatsby's file-system routing — any component under `src/pages/` becomes a route automatically (`index.tsx` → `/`, `404.tsx` → the 404 page). There's no custom router.
- **Shared layout**: `src/components/Layout.tsx` wraps page content in the `.paper-chrome`/`.paper-card` shell (dark page background behind an elevated "paper" card) and renders `src/components/ThemeToggle.tsx` and `src/components/BackgroundCredit.tsx` (attribution for the card's background texture) inside the card. Every page in `src/pages/` renders through it — there is no independent per-page markup/styling. Real resume content (contact card, experience, education, skills sections) hasn't been added yet; the pages currently render placeholder heading/copy through the shared shell. See [LAYOUT-SETUP.md](LAYOUT-SETUP.md) for the implementation history (font/color/theme-toggle choices and why they changed) behind this shell.
- **Light/dark theme toggle**: theme state lives entirely as a `data-theme="light"` attribute on `<html>` (absent = dark, the default) rather than React state — `ThemeToggle.tsx` renders identical markup on every render (both icons always in the DOM; CSS attribute selectors in `layout.scss` show/hide the right one) and flips the attribute imperatively via the DOM, so there's no hydration-mismatch risk from `localStorage`/`matchMedia` being unavailable during SSR. `gatsby-ssr.ts`'s `onRenderBody` injects a synchronous inline `<script>` into `<head>` (before `<body>` paints) that reads the `theme` key from `localStorage`, falls back to `matchMedia('(prefers-color-scheme: dark)')` if unset, and — only when unset — keeps listening for OS-level scheme changes; this exists because the site is statically generated with no per-visitor knowledge at build time, so without it there'd be a flash of the wrong theme on load. Persisted explicitly once the user toggles.
- **Styling**: `gatsby-plugin-sass` (registered in `gatsby-config.ts`) compiles `.scss` imported directly in component files. `Layout.tsx` imports `src/scss/layout.scss`, which uses the modern Sass module system (`@use './variables' as *; @use './typography';` — not the deprecated `@import`) to pull in the two partials `_variables.scss` (screen vs. print color variables, including the light-mode `$lavender-oxide` card background) and `_typography.scss` (Google Fonts `@import` for Lexend/Bitter, body/heading font rules — a plain CSS import for an external stylesheet, unrelated to the Sass module system). `layout.scss` also defines the `@media print` overrides (flips to a plain white page, drops the card's shadow/padding/background — `!important` on just the two theme-contested print declarations so light mode never leaks into print) and the `@page` size/margin rule. No separate PostCSS/Sass CLI config.
- **TypeScript**: `tsconfig.json` has `noEmit: true` — TS is used for type-checking only; Gatsby's internal Babel/Webpack pipeline handles actual transpilation. `strict: true` is enabled.
- **Extension points**: `gatsby-ssr.ts` (see theme toggle above) is the first of the three SSR/browser hook files `tsconfig.json`'s `include` anticipated; `gatsby-node.ts` and `gatsby-browser.ts` still don't exist. These remain the standard places to add programmatic page creation or browser-side APIs as the site grows beyond static pages.
- **Config**: site metadata and plugins are registered in `gatsby-config.ts` (currently just `gatsby-plugin-sass`).
